# Harness-4 进阶路线：从「单任务生成」到「自主交付 Loop」

> 命题：把 harness-4 现有的「单任务 Harness+Loop」两端接出去——入口接需求池，出口接 GitHub 与 ECS，形成「Spec 进 → 代码进仓库 → 测试 → 部署」的自主交付闭环。

---

## 一、先回答几个判断题

| 问题 | 回答 |
|---|---|
| 自动提交 GitHub、自动测试、部署 ECS 能实现吗？ | **能**，是 harness-4 的自然延伸，无需推翻现有架构 |
| 从需求池自己读任务、自动跑完再提交，可行吗？ | **可行**，即把「单任务 Loop」扩成「自主交付 Loop」 |

| 这些都能配置对吧？ | 对。模型 / 用例集 / 确定性 / 模式均已在 `config.env`，新增开关同理 |

## 二、现状定位：已经是完整的单任务 Harness+Loop

```
Harness(确定性脚手架):  constraints.json + rules/ + case.json + verify.py + gate.sh
Loop(反馈闭环):          generate → verify → 失败带日志重生成(≤3次) → 通过后确定性复跑
```

Loop 核心在 `generate.sh` 的 `for i in seq 1 MAX_RETRY` 重试段。**缺的不是 Loop，而是把 Loop 两端接出去**：

- **入口端**：现在手动 `bash gate.sh` + `constraints.json` 写死 `run_cases` → 进阶为「从需求池自动取任务」
- **出口端**：现在验收通过就停在 `output/` → 进阶为「自动 commit / push / 部署」

---

## 三、进阶路线（逐层叠加，每层可独立跑通）

### L1 — 通过即提交（最小、最先做）
在 `generate.sh` 的 `RESULT="pass"` 之后加一步：将 `output/<ts>-<case>/` 产物 `git add/commit`，push 到分支 `harness/<case>-<ts>`，可选自动开 PR。由 `config.env` 开关 `HARNESS_AUTOCOMMIT=1` 控制。投入最小，立刻见效。

### L2 — 需求池自主取任务
新增 `backlog/`（或 `backlog.jsonl`），每条为一个待做 case，带状态 `pending / running / done / failed`。写 `run_backlog.sh`：循环取 `pending` → 跑 `gate` → 成功标 `done` 并触发 L1 提交 → 失败标 `failed` 记原因。这即「自己从需求池读任务、自动去跑」。

### L3 — 提交触发 CI 测试
已有 `ci/github-actions.yml`。L1 push 后 CI 自动跑 `gate.sh`（离线 sample 闭环无需密钥，天然适合当 CI 门禁）。这块几乎白送。

### L4 — 部署到阿里云 ECS（CD）
CI 绿灯后，用 GitHub Actions 的 SSH deploy（`appleboy/ssh-action` 或自建 runner）把产物同步到 ECS 并重启服务。标准 CD，与 harness 解耦，最后接。

### 全景图

```
需求池 ──取任务──▶ [Harness+Loop 生成验证] ──通过──▶ git commit/push
   ▲                                                      │
   └──────── 失败回写状态/原因 ◀──────┘             触发 CI(gate.sh) ──绿──▶ 部署 ECS
```

## 四、qodercli vs DeepSeek —— 关键取舍

唯一模型耦合点在 `tools/run_model.py` 的 `call_deepseek`。换/加模型只需在此加 provider 分支，`config.env` 加 `HARNESS_PROVIDER=deepseek|qodercli` 开关。两者范式不同：

- **DeepSeek（现状，single-shot）**：一次生成文本 → 正则切文件（`<<<FILE>>>`）。**可控、易验证、易做确定性复跑**，与现有 `verify.py + 复跑比对哈希` 闭环天然契合。
- **qodercli（agentic CLI）**：自己读写文件、跑命令、多轮迭代。**更能啃复杂多文件任务**，但为黑盒 agent，输出发散、确定性弱，`seed/temperature` 复现基本失效。

**建议**：当前阶段留在 DeepSeek，因为 harness-4 的护城河正是「确定性 + 可验证复现」。等任务复杂到 single-shot 生成不动（多模块、跨文件重构、需跑命令）时，再把 qodercli 作为「重型 provider」接入，且**验证层不变**——不管谁生成，都必须过 `verify.py`。这才是 Harness 精神：**约束非确定性的生成，用可执行验证兜底**。

## 五、必须说明的边界（诚实声明）

harness-4 README 已声明：目前只锁定「列表+详情、读为主、Flask+Jinja+JSON」这一类场景。因此：

- 自动化流水线（读任务→生成→验证→提交→部署）**完全能搭起来**；
- 但**能自动跑通的任务类型仍受限于当前技术栈+结构抽象**。

要真正吃下任意需求，需先把抽象边界从「业务内容」上移到「技术栈+结构+验证策略」——这比自动化流水线更根本。

## 六、建议的下一步

先做 **L1（通过即自动提交）**：投入最小、闭环感最强，做完即可体会「Spec 进、代码进 GitHub」的自动交付感。

可选起点：
1. **L1**：给 `generate.sh` + `config.env` 加自动 commit/push（+可选开 PR）；
2. **L2**：搭 `backlog` 需求池 + `run_backlog.sh` 自主取任务。

实现风格遵循 harness-4 现有约定：**改配置不改产物**。
