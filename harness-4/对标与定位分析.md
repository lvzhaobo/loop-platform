## 一、平台能力对标

对照成熟"配置平台"通用能力清单(Terraform Cloud / Backstage / GitLab CI / Harness.io / Argo CD / Retool),harness-4 的现状与缺口:

| 维度 | 成熟平台的做法 | 我们现在 | 缺口 |
|---|---|---|---|
| **保存前校验** | 编辑即 lint + schema 校验,冲突当场报错 | `check_consistency.py` 只在门禁跑 | 编辑器里没有实时校验/红线,错到运行才发现 |
| **变更历史 / 回滚** | 每次改配置有 diff、作者、时间、一键回滚 | 靠 Git 手动 | 平台内无版本轴、无 diff、无回滚 |
| **密钥管理** | Vault / 加密 secret,永不明文 | `config.env` 里 key 明文 | 最该补的安全缺口(已做 Mock) |
| **运行可观测** | 历史运行列表、日志留存、趋势图 | `runs.jsonl` 有数据但无界面 | 缺"运行历史"页(已做 Mock) |
| **多环境分层** | dev/staging/prod 配置继承与覆盖 | 只有 base/task 两层规则 | 无环境维度 |
| **权限 / 审批** | 改硬约束需审批,RBAC | 无 | `constraints.json` 谁都能改,风险高 |
| **模板与复用** | 用例模板库、约束预设、导入导出 | cases 是静态目录 | 无"从模板新建用例"、无导出分享 |
| **通知 / 集成** | Slack/飞书/webhook 回传结果 | 无 | 门禁结果没法推给人 |
| **Dry-run / 预览** | 提交前沙箱试跑 | `generate.sh` 直接真跑 | 无低成本预演 |
| **字段级文档** | 每个配置项内联说明 + 示例 | 靠 md 文档 | 编辑器里无 inline 帮助 |

**优先级建议:**
1. 密钥不落明文(安全底线)—— ✅ 已做 Mock
2. 编辑器实时校验(把 `check_consistency` 前置到编辑态)
3. 运行历史页(把 `runs.jsonl` 可视化)—— ✅ 已做 Mock

> 这三个是"配置平台"和"一堆脚本"的本质区别。

## 二、业界 Harness / Loop 框架盘点

结论先行:**我们踩的三根支柱(spec 驱动 / 门禁 / 失败回喂 loop),业界每一根都有成熟且知名的代表,都不是首创。**

### 2.1 Spec 驱动这条线(和我们最像)

- **GitHub Spec Kit**(2025.9 开源)—— 几乎是我们思路的镜像:
  `Constitution(宪法/硬约束) → Specify → Clarify → Plan → Tasks → Implement`,
  并有 `/speckit.review` 作为过关质量门禁。它的 constitution ≈ 我们的 `constraints.json`。
- **AWS Kiro**(re:Invent 2025)—— 专门做的 spec-driven AI IDE,spec 作为事实源派生代码,主打"outcome 比实现细节重要"。
- **BMAD method** —— 另一套把 spec 流程模板化的方法论。

### 2.2 Loop / 自动修复这条线

- **Meta TestGen-LLM** —— 生成 → 跑测试 → 只留通过的,工业级落地。
- **RepairAgent**(ICSE 2025)—— 自主 LLM agent 做程序修复的循环。
- **LLMLOOP / 各种 self-refine 框架** —— 失败信息回喂、迭代重生成,论文与开源一大把。

### 2.3 确定性 / 可复现这条线

- **Nix / Bazel** —— hermetic build,同输入必同输出,哈希校验。我们的 `runs.jsonl` 复跑比对就是同一思想搬到 codegen 上。
- **Terraform `plan`** —— 确定性预演后再 apply。

## 三、我们到底有没有创新(诚实版)

### 3.1 必须承认不新的部分(占大头)

- "契约作为唯一事实源" → Spec Kit 的 constitution + spec 已经是这套。
- "不过关不放行的门禁" → Spec Kit 有 `/review`,所有 CI 也有。
- "失败回喂重试" → 论文/产品遍地都是。

> 如果说"我们发明了 spec 驱动 / 门禁 / loop",不成立,会被懂行的人当场戳穿。

### 3.2 相对有差异、但算不上范式级创新的部分(占小头)

1. **把"确定性"当成一等验收维度** —— `temperature=0` + `seed` + 复跑哈希比对,把可复现性像 lint/test 一样纳入门禁。多数 spec-driven 工具不强调确定性(LLM 本来就不稳),这点我们更偏工程严谨,类似 Nix/Bazel 的 hermetic 思路。
2. **自洽性门禁前置到"调模型之前"** —— `check_consistency.py` 在花钱调模型前,先卡住"case.json 每条事实必须在 spec 有落点"。多数工具是生成后再 review;我们是生成前先证伪,省 token 也更早失败。
3. **收敛成"可配置工作台"的产品化** —— Spec Kit 是 CLI,Kiro 是 IDE;我们想做面向非专家、可视化配置约束/规则/用例的控制台。这是工程整合与 UX 取向上的差异,不是算法创新。

### 3.3 一句话总结

> 我们不是在发明新范式。"spec 驱动 + 门禁 + loop"这个组合,Spec Kit 已经基本占住。
> 真正能立得住的差异点只有两个半:①确定性/可复现做成硬性验收;②门禁在调模型前就前置证伪;③(半个)包装成可配置工作台。
> 这些是"更严谨的工程选择",不是"从没人做过的创新"。

### 3.4 若想要真创新,往哪使劲

- **确定性即合约**:同 spec 在不同模型/不同时间跑,产物哈希可比对、可回归 —— 做成"codegen 的可复现性基准",业界稀缺。
- **事实源 ↔ 产物的双向可追溯**:改一条 case 事实,精确算出影响哪些 spec、哪些产物文件、哪些测试。

## 四、Loop Engineering 体系与我们的定位

### 4.1 背景:Loop Engineering 是什么

- 前身:Geoffrey Huntley 的 **"Ralph Wiggum"** 技术(2025.5)—— 一个 bash while 循环反复给 agent 相同 prompt,每轮重置上下文,用文件系统(而非对话历史)当记忆。
- 爆发:2026.6,Boris Cherny(Claude Code 创建者)、Peter Steinberger(OpenClaw)、Addy Osmani(Google Chrome)同周表态。核心判断:
  > "You shouldn't be prompting coding agents anymore. You should be designing loops that prompt your agents."
- 定义:设计一个系统,让它按 **schedule** 和 **goal** 自动提示 agent,而不是人类手动逐轮输入。

### 4.2 关键:Osmani 的工程层级(直接印证我们的命名)

```
┌─────────────────────────────────────────────┐
│  Loop Engineering                            │ ← 设计自主系统(调度/验证/状态/护栏)
│  (在 harness 之上自运行、生成子 agent、自我供给)   │
├─────────────────────────────────────────────┤
│  Agent Harness Engineering                   │ ← 设计单个 agent 运行的环境   ★ 我们的 harness-4
│  (工具、权限、沙盒、上下文管理)                    │
├─────────────────────────────────────────────┤
│  Context Engineering                         │ ← 管理上下文窗口(RAG/文档/历史)
├─────────────────────────────────────────────┤
│  Prompt Engineering                          │ ← 优化单轮指令(措辞/格式/few-shot)
└─────────────────────────────────────────────┘
```

> 我们项目命名 harness + loop 不是巧合:正好踩在这套体系相邻的第 3、4 层。

### 4.3 Loop 的六个原语(以前写 bash,现在内建进产品)

1. **Automations** —— 定时发现 + 分派(Claire Vo 分四类:heartbeat / cron / hook / goal)
2. **Worktrees** —— git worktree 隔离并行 agent
3. **Skills** —— SKILL.md 沉淀项目知识(解决 Intent Debt)
4. **Plugins / Connectors** —— MCP 连接真实工具(issue、DB、Slack)
5. **Sub-agents** —— Maker/Checker 分离(写的和验收的用不同模型/指令)
6. **Memory / State** —— 对话之外的状态文件(markdown / Linear)

### 4.4 各平台的创新与结合

| 平台 | 关键创新 / 结合 |
|---|---|
| **Claude Code**(Anthropic) | `/goal`(目标循环,独立小模型判停,避免自评)、`/loop`(cron 式)、hooks、**Routines(loop 搬到服务端)** |
| **OpenAI Codex** | Automations(定时)、**Worktree 隔离**、Triage 收件箱、只读/受限沙盒 |
| **OpenClaw**(Steinberger) | 开源完整 loop 架构,GitHub 史上最快 star 新仓库 |
| **Hermes Agent**(Nous Research) | ReAct runtime loop + cron + skills + 子 agent |
| **TrueFoundry** | 企业级 harness + **AI FinOps(预算/配额/限速)** + MCP Gateway |

被反复验证的设计模式:
- **Maker-Checker 分离** —— "Done is a claim, not a proof"
- **可验证停止条件写成"合同"** —— 终态 / 证据 / 约束 / 预算 四要素
- **验证成本阶梯**(Blake Crosley)—— "loops win where verification is cheap"
- **三条强制护栏** —— 硬迭代上限 + diff 检查 + 花费上限(Uber 4 个月烧光全年 AI 预算的教训)

### 4.5 有没有类似我们的平台(实事求是)

**结论:概念层上有,精确对应的产品没有。**

我们命中的(和主流一致):
- 我们的 **loop 模式 = 教科书式的 "Closed Loop"**(路线预映射、固定脚手架内迭代、可预测成本),正是"生产默认"模式。
- 我们的 **`verify.py` 门禁 = 可验证停止条件**;`constraints.json` = guardrails;loop 迭代上限 = 护栏。
- 血统上,**我们的 loop 是一个"更规矩的 Ralph Wiggum"**:文件系统当记忆、每轮重置、跑到验证通过为止。

我们缺的(主流 loop 平台都有,我们没有):
- ❌ 调度(heartbeat/cron/hook)—— 我们只有手动触发
- ❌ Worktree 并行多 agent —— 我们是单发
- ❌ **Maker-Checker 用第二个 LLM** —— 我们的验收是确定性脚本,不是对抗式 LLM reviewer
- ❌ Connectors/MCP 去开 PR、发飞书 —— 没有
- ❌ 服务端 loop、FinOps 成本治理 —— 没有

最像我们的:
- **GitHub Spec Kit** —— 在"spec/宪法 + 门禁"这半边高度重合(偏 harness 层,不强调 loop 自运行)。
- **Ralph Wiggum 技术** —— 我们 loop 模式的思想祖先。
- 但"窄任务(spec→应用 codegen)+ 确定性哈希验证的门禁作为 loop 停止条件"这个精确组合,找不到一个现成知名产品完全对应。

**诚实的自我定位:**
> 我们是一个专注单一任务的 harness(第 3 层)+ 一个验证门禁驱动的闭环(第 4 层的一个原语);
> 而 Claude Code / Codex 是通用的 loop 平台。我们不是同级别的东西——**他们做宽,我们做深且窄。**

**真正站得住的点:**
> 主流明说 token 消耗"高度可变、本质随机"(斯坦福研究:同任务能差 30 倍),他们放弃了确定性;
> 而我们把确定性/可复现做成硬验收。同时 Blake Crosley 的"验证便宜的地方 loop 才赢"——
> 我们的验证恰恰是最便宜的确定性脚本,不是烧钱的第二个 LLM。
> 所以从 loop engineering 理论看,我们这个 loop 的"验证经济学"是很正的,这不是蹭概念,是真契合。

## 五、结论与后续方向

**一句话定位:**
> 我们没发明新范式,是 Loop/Harness 体系里一个"窄而确定"的实例;
> 真正的差异化护城河是"确定性验收 + 廉价验证",而不是流程本身。

**后续可做(按价值排序):**
1. 编辑器实时校验(check_consistency 前置到编辑态)
2. 运行历史接真实 `runs.jsonl`(已有 Mock)
3. 密钥接后端加密存取(已有 Mock,纯前端不够)
4. 变更历史 / 审计(diff + 回滚)
5. 仪表盘首页升级(通过率趋势、最近运行、待办告警)
6. 模板库、通知集成(成本低,随时可加)
7. 暂不做:多环境分层、审批/权限(改动大,依赖真实后端,纯 Mock 价值低)

**若要做真创新,聚焦两点:**
- 确定性即合约(跨模型/跨时间的产物哈希回归基准)
- 事实源 ↔ 产物的双向可追溯(改一条事实,精确定位影响面)
