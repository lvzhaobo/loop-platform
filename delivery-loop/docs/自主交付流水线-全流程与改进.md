# 自主交付流水线：从飞书需求到 ECS 上线的全流程

> 一句话：**在飞书 Wiki 写一条需求 → 自动生成代码并验证 → 推送 GitHub → 部署到阿里云 ECS 公网可访问**。
> 线上验证地址（多样例并存，B 方案）：<http://<your-server-ip>:1001/>（sample1）、<http://<your-server-ip>:1002/>（sample2），均返回 HTTP 200。

---

## 1. 这套东西是什么

我们在既有的 **harness-4**（契约驱动的确定性代码生成 + 验证框架）之上，新增了一个**独立的编排层 `delivery-loop/`**，把「需求 → 代码 → 验证 → 发布 → 部署」串成一条可自动运行的流水线。

设计上的一条硬约束：

> **`delivery-loop` 把 harness-4 当黑盒引擎调用（`bash harness-4/generate.sh`），不 import 其内部代码、不改其任何产物。**

这样做的好处：harness-4 可以独立演进/替换，编排层只依赖它的「命令行 + 退出码 + `output/runs.jsonl`」这层稳定契约。

### 分层职责

| 层 | 组件 | 职责 |
|---|---|---|
| 需求来源 | `adapters/`（local / feishu） | 从需求池取任务、回写状态 |
| 编排 | `orchestrator.py` | 取任务 → 调引擎 → 发布 → 部署 → 回写 |
| 引擎 | `harness-4/`（子进程） | 生成代码 + 验收 + 确定性校验 |
| 发布 | `publisher.py` | 产物推送到 GitHub（子目录 / 分支模式） |
| 部署 | `deployer.py` | 拉取式部署到 ECS（SSH + git pull + 重启） |
| 触发 | `trigger/`（poll / webhook） | 把「人工跑批」升级为「自驱动 Loop」 |

## 2. 端到端流程图

```
飞书 Wiki 需求(Spec)
      │  ① 飞书开放 API 直连读取
      ▼
adapters/feishu_adapter.py ──► 需求任务(Task: case=education)
      │  ② orchestrator 取任务
      ▼
harness-4/generate.sh (子进程) ──► 生成 Flask 应用 + 20/20 验收 + 确定性字节一致
      │  ③ HARNESS_AUTOCOMMIT=1
      ▼
publisher.py ──► GitHub: lvzhaobo/loop-sample 的 sampleN/ 目录 @ main（B 方案:每次自动递增 sample1→2→3…)
      │  ④ ECS_DEPLOY=1（推送成功后触发）
      ▼
deployer.py ──► SSH 到 ECS → git pull → pip install → nohup 起 app.py（端口=1000+N，部署后只保留最近 5 个进程）
      ▼
http://<your-server-ip>:100N/   ✅ 公网可访问（sample1→1001, sample2→1002…）
```

对应四段能力（在 `config.env` 里用开关逐段打开）：

- **取需求**：`HARNESS_BACKLOG_SOURCE=feishu`
- **生成+验证**：`HARNESS_MODE=sample`（离线零成本）/ `real`（调 DeepSeek）
- **发布**：`HARNESS_AUTOCOMMIT=1` + `HARNESS_GIT_*`（B 方案:`HARNESS_GIT_SUBDIR_AUTO=1` 默认开，自动递增 sampleN）
- **部署**：`ECS_DEPLOY=1` + `ECS_*`（端口 `HARNESS_PORT_BASE`+N，保留最近 `ECS_RETAIN` 个）

## 3. 每一段是怎么打通的

### ① 飞书 Wiki 取需求

- 用户给的是**知识库 Wiki 链接**（`/wiki/<node_token>`），不是普通云文档（`/docx/<id>`）。
- Wiki 节点不能直接读正文，需要先用 `wiki/v2/spaces/get_node` 把 `node_token` 解析成底层的 `obj_token`（docx id），再用 `docx/v1/documents/{id}/raw_content` 读正文。
- 适配器新增了 `_wiki_obj_token()` 和 `_resolve_content()`，`feishu_docs.json` 里既支持 `doc_token` 也支持 `wiki_token`。
- 运行时**直连飞书开放 API**（`tenant_access_token` 换 token → Bearer 调用），不走 MCP —— 独立进程用不了 MCP，MCP 仅供开发期验证。

### ② harness-4 生成 + 验证

- 编排层把飞书需求映射到 harness-4 的 `education` 用例，子进程执行 `HARNESS_CASES=education bash harness-4/generate.sh`。
- 结果通过退出码 + `output/runs.jsonl` 回读：**20/20 验收通过、两次生成字节一致（确定性）**。
- 产物落在 `output/<时间戳>-education/`（含 `app.py` / `templates/` / `static/` / `tests/` / `requirements.txt`）。

### ③ 发布到 GitHub（子目录模式 + B 方案自动递增）

- 选择**子目录模式**：一个仓库 `loop-sample` 收纳多个样例，应用写进 `sampleN/`。
- **B 方案（`HARNESS_GIT_SUBDIR_AUTO=1`，默认开）**：克隆目标仓后扫描已有 `sampleN` 取 max+1，**每次发布新建下一个目录**（sample1→sample2→sample3…），**不覆盖旧样例**；旧版本天然留在 git 历史里。
- 流程：克隆目标仓 → 算出新 `sampleN/` → 写入 → 提交 → 推送 main；同时回填 `subdir`/`port`(=`HARNESS_PORT_BASE`+N) 供部署层使用。
- 想回退到「固定单目录覆盖」(A 方案)：设 `HARNESS_GIT_SUBDIR_AUTO=0` + `HARNESS_GIT_SUBDIR=sample1`，代码两种模式都兼容。

### ④ 部署到 ECS（拉取式 + 端口规则 + 保留策略）

- 与用户约定**拉取式**：代码已在 GitHub，ECS 侧 `git pull` 后运行，不 scp 源码。
- 远端脚本：`git clone/pull` → 进 `sampleN/` → `pip install` → 杀旧进程（`app.pid` 按子目录隔离）→ `PORT=<1000+N> nohup python3 app.py`。
- **端口规则**：每个样例端口 = `HARNESS_PORT_BASE`(默认 1000) + N，即 sample1→1001、sample2→1002…（ECS 安全组需放行该段，如 1001–1099）。
- **保留策略（`ECS_RETAIN`，默认 5）**：部署后只保留**最近 5 个样例进程存活**，更旧的自动停进程、腾端口；**目录本身留在 git 不删**（可随时重新拉起）。

## 4. 踩过的坑与修复（真实记录）

| 问题 | 现象 | 修复 |
|---|---|---|
| 飞书 Wiki 读不了 | 适配器只认 `/docx/`，用户给的是 `/wiki/` | 加 Wiki 节点解析（get_node → obj_token） |
| 飞书 400 报错笼统 | 只看到 `HTTP Error 400` | `_send` 捕获 HTTPError 解析 JSON 错误体，暴露真实错误码 `99991672`（缺 Wiki 权限） |
| 飞书权限不足 | 应用没有 wiki / docx scope | 开放平台加 `wiki:node:read` + `docx:document:readonly` 并发布版本 |
| GitHub 推送 HTTP2 报错 | `Error in the HTTP2 framing layer` | git 命令级加 `-c http.version=HTTP/1.1`（不改全局配置） |
| GitHub 推送被拒 | `Permission ... denied` | PAT 的 **Contents** 权限从只读改为 **Read and write** |
| sshpass 装不上 | macOS 默认 brew 已下架，paramiko 在 Python 3.14 无预编译包 | 改用 **Python 标准库 `pty`** 驱动系统 `ssh` 喂密码，**零依赖** |
| 内容一致时不部署 | 「无变更」分支没标 pushed，部署被跳过 | 「内容与远端一致」也视为已发布，照常触发部署 |

**贯穿始终的两条工程原则**：

1. **凭证安全**：密钥（`DEEPSEEK_API_KEY` / `GITHUB_TOKEN` / `FEISHU_APP_SECRET` / `ECS_SSH_PASSWORD`）统一放仓库根 `.env`（已 gitignore），**绝不进 `config.env`**（会提交）。日志中 token/密码一律替换为 `****`。
2. **诚实**：错误原样透出（如飞书权限错误码、部署失败日志尾部），不吞异常、不假装成功。

## 5. GitHub Actions 自动部署（已验证 ✅）

除了本地 `delivery-loop` 触发部署，还配了一条 **GitHub 侧的 CI**（已升级为**通用多样例版**）：任意 `sample<N>/**` 变更推到 main（含 PR 合并）时，GitHub Actions 自动识别本次改动的 `sampleN` 目录、按端口=1000+N 部署，并保留最近 5 个进程。**已实跑验证成功**（通用版 workflow run #4 conclusion=success）。

- 源文件：`delivery-loop/ci/loop-sample-deploy.yml`；已上传到仓库根 `.github/workflows/deploy.yml`。
- 通用化关键：触发从 `sample1/**` 放宽为 `sample*/**`；job 先用 `git diff` 算出本次改动的 sampleN（取不到时回退部署最高编号），再逐个部署。**新增 sample8/sample9… 无需改 workflow**。
- 需在 `loop-sample` 仓库网页手动完成的两件事：
  1. workflow 文件：本可网页创建；实际是给 PAT 补了 **Workflows: write** 权限后用 Contents API 上传的。
  2. 添加 Secrets：`ECS_HOST` / `ECS_SSH_USER` / `ECS_SSH_PORT` / `ECS_SSH_PASSWORD`（Secrets 只能网页加，token 碰不了）。
- 与本地部署**幂等共存**（都是拉取式 + `app.pid` 隔离 + 端口=1000+N），互不影响。

### 现在有两条独立的自动部署通道

| 通道 | 触发方式 | 状态 |
|---|---|---|
| 本地 delivery-loop | 命令行跑批（飞书取需求→生成→推送→部署） | ✅ 已验证 |
| GitHub Actions CI | `sample*/**` 推到 main（含 PR 合并）自动触发，多样例自适应 | ✅ 通用版 run #4 成功 |

### 触发时的一个坑（已绕过）

用 API 触发 `workflow_dispatch` 需要 token 的 **Actions: write** 权限（和 Workflows write 不是一回事）。为免再加权限，改用**推一个 `sample1/.deploy-trigger` 标记文件**触发 push 事件——只用已有的 Contents 写权限即可激活 workflow。该标记文件无害，可随手删除。

## 7. 后续可以改进的地方

### 7.1 配置体验（最高优先级）

现在端口 1001、ECS IP、GitHub 仓库这些都靠**手改 `config.env` / `.env` + 记一串 export**，门槛高、易错。
**需要一个配置界面**：网页表单里填端口 / IP / 仓库 / 触发开关，点保存即生效。
> 详见配套文档：[配置界面-必要性与设计.md](./配置界面-必要性与设计.md)

### 7.2 自由文本 Spec → 真实生成

目前是「需求条目 → 预设 case（education/blog/ecommerce）→ 跑固定用例」。
真正的「飞书里写任意 Spec 文本 → 自动生成对应应用」还差一步 **spec 编译**（把自然语言 Spec 解析成 harness-4 的契约/schema）。代码里已诚实留了这个断点（`orchestrator.py` 的 `fetched` 分支）。

### 7.3 从「人工跑批」到「自驱动 Loop」

`trigger/`（poll 轮询 + webhook 事件）已就位但未接入日常。补上后，飞书一有新需求就自动跑，才算真正的 Loop Engineering。

### 7.4 部署健壮性

- 目前 `nohup python3 app.py` 裸跑，重启机器不自动拉起。可升级为 **systemd 服务** 或 **Docker 容器**。
- 缺**回滚**：部署失败应能自动回到上一个可用版本（记录上次 commit）。
- 缺**健康检查闭环**：部署后应自动 `curl` 探活并把结果回写到需求来源。

### 7.5 多样例 / 多环境

- ✅ **多样例已实现（B 方案）**：一仓多 `sampleN/`、端口=1000+N、`app.pid` 按子目录隔离、保留最近 5 个进程、通用 workflow 自适应。见 §3③④ 与 §5。
- 待做：端口可升级为**注册表**（目录→端口映射持久化，本地与 workflow 共用一份）；可加一个列出所有样例 + URL 的索引页。
- 待做：区分 staging / prod 环境。

### 7.6 可观测性

- 现在结果打在终端 + `feishu_state.json`。可加一份**结构化运行台账**（每次 run 的耗时/重试/产物/部署 URL），并在界面上展示历史。

### 7.7 安全加固

- GitHub token 曾在协作过程中明文出现，建议**定期轮换**并用最小权限细粒度 PAT。
- ECS 密码登录建议逐步换成 **SSH 密钥**；webhook 对外时必须加鉴权 + HTTPS。
