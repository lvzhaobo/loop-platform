# 配置界面：必要性与设计草案

> 记录动机：当前把应用部署端口写死成 **1001**、ECS IP / GitHub 仓库 / 各种开关都散落在 `config.env` 和 `.env` 里，靠**手改文件 + 记一串 `export`** 才能跑。这条链路已经能跑通了，但**配置方式太原始**，是接下来最该打磨的一块。本文记录「为什么需要配置界面」以及初步的设计思路，供后续实现。

---

## 1. 为什么必须要有配置界面

### 痛点 1：端口/参数写死，改起来靠记忆

现在要把端口从 1001 换成别的，得知道：
- 改 `config.env` 里的 `ECS_APP_PORT`，或
- 运行前 `export ECS_APP_PORT=xxxx`，还要记得同时改 GitHub Actions（`.github/workflows/deploy.yml` 里也硬编码了 `APP_PORT=1001`）和阿里云安全组放行。

**同一个「端口」概念散落在 3 个地方**（config.env / workflow / 安全组），改一处漏两处，极易出错。

### 痛点 2：配置分散在多个文件、多种介质

| 配置 | 现在放在哪 |
|---|---|
| 端口 / ECS IP / 仓库 / 开关 | `delivery-loop/config.env` |
| 密钥（token/密码） | 仓库根 `.env` |
| CI 里的端口 / 仓库 | GitHub `deploy.yml`（远端仓库） |
| 端口放行 | 阿里云安全组控制台 |

要完整配一次，得在 4 个地方之间来回切换，认知负担高，新人几乎无法独立操作。

### 痛点 3：没有校验与即时反馈

手改文件不会告诉你：
- 端口是否被占用 / 是否在安全组放行；
- ECS 密码对不对（要等跑到部署那步才报错）；
- GitHub token 权限够不够（要等推送被拒才知道）。

**错误发现得太晚**，每次都要跑一遍完整流水线才暴露配置问题。

### 痛点 4：状态不可见

当前运行结果只打在终端 + `feishu_state.json`。没有一个地方能一眼看到：
- 现在配了哪些参数、上次跑成功没、线上服务活着没、部署在哪个 URL。

---

## 2. 配置界面要解决什么（目标）

> **一句话目标：让「配一次、跑起来、看状态」都在一个网页里完成，不再手改文件。**

- **表单化配置**：端口 / ECS IP / 仓库 / 各段开关，网页填写、点保存即写回 `config.env`（密钥单独走安全通道写 `.env`）。
- **单一事实源**：端口等「一处定义、多处引用」的参数，界面统一管理，自动同步到 config / workflow（或运行时注入），消除「改一处漏两处」。
- **保存前校验**：端口占用检测、ECS 连通性/密码探测（试连一次）、GitHub token 权限检查、安全组放行提示。
- **一键运行 + 实时状态**：页面上点「跑一次」，实时看日志；展示上次 run 的产物 / 提交 / 部署 URL / 探活结果。
- **密钥安全**：密钥输入框只写不回显（写入 `.env`，页面永不展示明文），与非机密配置在存储上分离。

## 3. 初步设计草案

### 3.1 界面分区

```
┌─ 需求来源 ────────────────────────────┐
│ 来源: [feishu ▼]  文档清单: feishu_docs.json  [编辑]│
├─ 生成引擎 ────────────────────────────┤
│ 模式: (●) sample 离线   ( ) real 调 DeepSeek       │
├─ 发布 GitHub ─────────────────────────┤
│ 仓库: github.com/lvzhaobo/loop-sample.git          │
│ 布局: (●) 子目录 [sample1]  ( ) 分支                │
│ 分支: main    [✓] 推送到远端                        │
├─ 部署 ECS ────────────────────────────┤
│ [✓] 启用部署   IP: 47.76.211.100   端口: [1001]   │
│ 用户: root  SSH端口: 22  密码: ******** [测试连接]  │
├─ 密钥(写入 .env,不回显) ──────────────┤
│ GITHUB_TOKEN: ********  FEISHU_SECRET: ********     │
├─ 触发器 ──────────────────────────────┤
│ ( ) 手动   (●) 轮询 每 [300] 秒   ( ) Webhook       │
└───────────────────────────────────────┘
         [保存配置]   [跑一次]   [查看运行历史]
```

### 3.2 存储与写回

- **非机密配置** → 写回 `delivery-loop/config.env`（保持现有 `${VAR:-default}` 格式，界面只覆盖值）。
- **密钥** → 写回仓库根 `.env`，页面只接受输入、永不读回明文；已配置的显示为 `已设置`。
- **端口这类跨处引用**：界面存一份权威值，运行时注入 `ECS_APP_PORT`；生成/更新 workflow 时也从这份值渲染，避免硬编码漂移。

### 3.3 技术选型建议（轻量优先）

- 后端：**Flask**（与生成的应用同栈，零新增依赖门槛），几个接口即可：
  - `GET /api/config`（读当前非机密配置）
  - `POST /api/config`（校验后写回 config.env）
  - `POST /api/secrets`（只写 .env，不回显）
  - `POST /api/run`（触发一次 `run_backlog.sh`，SSE/WebSocket 推日志）
  - `GET /api/status`（上次 run 结果 + 线上探活）
- 前端：先做**单页静态 HTML + 原生 JS**（够用、无构建），后续再考虑框架。
- 复用已有的 `harness-4/studio/`（那里已有 server.py + 前端原型），可以在其基础上扩展，而不是从零搭。

### 3.4 校验清单（保存/运行前）

| 项 | 校验方式 |
|---|---|
| 端口格式/范围 | 1–65535 数字 |
| 端口占用 | 部署前 SSH 到 ECS `ss -ltn` 查该端口 |
| ECS 连通性 | 试 SSH 连一次（超时/密码错即时反馈） |
| GitHub token | 调 API 查仓库 + 权限（Contents 写是否具备） |
| 安全组 | 无法自动查时，给出明确提示「请在阿里云放行 TCP <端口>」 |

---

## 4. 优先级建议

1. **P0**：端口 + ECS + 仓库 的表单配置 + 保存写回 + 「跑一次」按钮 —— 直接消灭「手改文件」痛点。
2. **P1**：保存前校验（连通性/端口/权限）+ 运行状态与探活展示。
3. **P2**：触发器可视化开关、运行历史台账、密钥安全输入。
4. **P2**：端口「单一事实源」自动同步到 GitHub workflow。

---

## 5. 与现有架构的关系

- 配置界面是**又一个纯外挂层**，和 `trigger/` 一样：只读写 `config.env` / `.env`、只调用 `run_backlog.sh`，**不改 `orchestrator.py`、不碰 `harness-4`**。
- 这样保持了整套系统「编排层薄、引擎黑盒」的一致设计，界面坏了也不影响命令行照常跑。

## 6. 实现记录：需求池面板（已落地）

> 第一块落地的界面能力。位置在 studio 配置工作台（`harness-4/studio/`，`http://<host>:5100`）**左栏顶部「需求池」面板**。纯新增外挂：只读写 `feishu_docs.json` / `feishu_state.json`，不 import 适配器、不碰 orchestrator/引擎；前端为自包含内联脚本，不改 `studio.js`。

### 6.1 能力

- **清单可视化**：把 `feishu_docs.json`（需求清单）与 `feishu_state.json`（处理状态）合并展示。每条显示状态徽章（`pending` / `✔ done` / `✘ failed`）、标题，以及元信息 `FS-001 · P1 · sample3:1003 · 1 次`（发布的样例目录:端口、尝试次数）。
- **贴链接新增**：填标题（可选）+ 飞书文档链接 →「加入需求池」。自动解析 token、生成 `FS-NNN`、写回 `feishu_docs.json`。
- **重跑**：已完成项一键清除其状态（从 `feishu_state.json` 移除）→ 重新变 `pending`，下次交付会重新生成（解决「done 后待办=0、无法再跑」）。
- **移除**：从需求池删除一条并清掉其状态记录。

### 6.2 后端接口（`harness-4/studio/server.py`）

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/backlog` | 合并 docs+state，返回清单与状态、来源 |
| POST | `/api/backlog` | 新增：`{title?, link, priority?, force?}` |
| POST | `/api/backlog/<id>/reset` | 清状态→重新 pending（重跑）|
| DELETE | `/api/backlog/<id>` | 移除该条并清状态 |

路径取自 `config.env` 的 `HARNESS_FEISHU_DOCS` / `HARNESS_FEISHU_STATE`，与命令行、webhook 是**同一份文件**。

### 6.3 链接解析规则

| 输入 | 解析为 |
|---|---|
| `.../wiki/<token>` | `wiki_token`（知识库节点，最常见）|
| `.../docx/<token>` 或 `.../docs/<token>` | `doc_token` |
| 直接粘贴纯 token（无斜杠）| 按 `wiki_token` |
| 其它 | 400，提示无法解析 |

### 6.4 重复策略：允许重复，但先提示

- **允许**同一文档重复加入——文档内容会更新、也可能故意拿同一文档多次生成；每条各自一个 `id` 与独立状态，互不干扰。
- 但**默认检测重复**：新增时若该 token 已存在且请求未带 `force`，后端返回 `409 {duplicate:true, existing:[id...]}`；前端弹确认「该文档已在需求池中(FS-xxx)，内容可能已更新。仍要再加一条吗？」，确认后带 `force:true` 重新提交才真正追加。
- 副作用提醒：去掉硬去重后，重复项都会在下次「开始交付」时**逐条各跑一次**（各自生成、各自推一个 sample），不想要的用「✕ 移除」删。
