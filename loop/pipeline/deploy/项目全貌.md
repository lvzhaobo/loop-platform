---

## 一、一句话是什么

**点一个按钮,飞书里的需求文档自动变成一个跑在公网上的真实应用。**

整条流水线全自动:读需求 → LLM 编译成规格契约 → LLM 真实生成代码 → 自动验收(还跑两遍校验产物一致性)→ 推 GitHub → 自动部署到 ECS → 线上访问。

---

## 二、整体方案(五层架构)

```
┌─────────────────────────────────────────────────────────────────┐
│  ① 需求源     飞书 Wiki 文档  /  本地 backlog.jsonl               │
│     adapters/feishu_adapter.py  →  统一成 Task 对象                │
└───────────────────────────┬─────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│  ② 编排层  loop/pipeline/orchestrator.py (主循环 / 大脑)          │
│     取任务 → 编译 Spec 成 case → 调引擎 → 发布 → 回写状态          │
│     把 loop/engine 当【黑盒引擎】调用,不 import 其内部、不改其产物   │
└───────────────────────────┬─────────────────────────────────────┘
                            ↓ subprocess: bash loop/engine/generate.py
┌─────────────────────────────────────────────────────────────────┐
│  ③ 生成引擎  loop/engine (真正干活的地方)                           │
│     generate.sh → run_model(LLM 生成代码)                        │
│                 → verify.py / verify_ac.py(自动验收)             │
│                 → 确定性校验(同一输入跑两遍,产物必须字节一致)     │
└───────────────────────────┬─────────────────────────────────────┘
                            ↓ 验收全过
┌─────────────────────────────────────────────────────────────────┐
│  ④ 发布层  publisher.py → 推到 loop-sample 私有仓 sampleN/ @ main │
└───────────────────────────┬─────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────────┐
│  ⑤ 部署层  GitHub Actions「Deploy samples to ECS」/ deployer.py   │
│     ECS 拉取 sampleN → 起进程 → 端口 1000+N 上线                   │
└─────────────────────────────────────────────────────────────────┘
```

**关键设计原则**:编排层(loop/pipeline)与引擎层(loop/engine)彻底解耦——编排层只通过
`bash generate.sh` + 退出码 + `output/runs.jsonl` 跟引擎打交道,永不碰引擎内部代码。
这样引擎可独立演进,编排可独立扩展需求源/发布目标。

### 两种"生成形态"(理解这个才懂番茄钟那个坑)

| 形态 | 触发条件 | 生成什么 | 用哪个验收器 |
|---|---|---|---|
| **catalog 目录站** | 有 `case.json` | 列表 + 详情页(≥N 条数据的数据站) | `verify.py` |
| **Spec 交互工具** | 有 `spec/manifest.json` + `acceptance.json` | 单页交互应用(如番茄钟计时器) | `verify_ac.py` |

由 `feishu_docs.json` 里该需求的 `archetype` 字段决定(`spec` = 交互工具,缺省 = catalog)。
**这是"人来定性"的一步**:番茄钟必须人工标 `archetype=spec`,否则会被默认套成 8 张卡片的列表站。

## 三、ECS 上跑着什么(运行态全景)

### 3.1 四类常驻进程

| 进程 | 端口 | 是什么 | 监听地址 | systemd 服务名 |
|---|---|---|---|---|
| **loop-studio** | 5100 | 完整配置平台(约束/用例编辑 + 一致性预检 + 🚀开始交付按钮) | `0.0.0.0`(已开公网) | `loop-studio.service` |
| **loop-platform** | 8787 | 极简"跑一批"webhook 按钮页 | `127.0.0.1`(仅隧道) | `loop-platform.service` |
| **loop-spa** | 5200 | 精美 SPA 前端(Dashboard/需求/Trace),打 5100 的 API | `127.0.0.1`(仅隧道) | `loop-spa.service` |
| **sampleN** | 1000+N | 每次交付产出的真实应用(如番茄钟在 1008) | `0.0.0.0`(公网) | 由部署脚本拉起 |

> 三个平台服务都由 `setup_ecs.sh --with-service` 一次性装成开机自启 + 崩溃自拉起。
> 每个 `ExecStart` 都先 `source .env + config.env` 再启动,保证每一批交付都拿得到密钥。

### 3.2 当前线上入口

- **配置平台(可点交付)**: http://47.76.211.100:5100 (口令登录,`STUDIO_TOKEN`)
- **番茄钟成品示例**: http://47.76.211.100:1008

## 四、让 Loop Platform 跑起来的全部文件

> 按"层"分组。这是 ECS 上 `/root/loop-platform` 里真正参与运行的文件清单
> (排除 `.venv`、`output/` 产物、`__pycache__`、文档)。

### 4.1 编排层 `loop/pipeline/`(大脑)

| 文件 | 作用 |
|---|---|
| `orchestrator.py` | **主循环**。取任务→编译 Spec→调引擎→发布→回写状态。整个平台的入口 |
| `config.env` | 编排层配置默认值(需求源/生成模式/发布开关/端口基数…),环境变量可覆盖 |
| `run_backlog.sh` | "跑一批"外壳脚本,source 环境后调 orchestrator |
| `publisher.py` | 发布层:把产物推到 loop-sample 仓 sampleN,自增 N,回填 publish 信息 |
| `deployer.py` | 部署层:SSH 到 ECS 拉取式部署(用 pty 驱动 ssh/scp 喂密码) |
| `adapters/base.py` | `Task` 数据结构 + 适配器基类 + `load_adapter` 工厂 |
| `adapters/feishu_adapter.py` | **飞书适配器**:读飞书 Wiki docx → Task;未知字段(如 archetype)落入 `task.extra` |
| `adapters/local_adapter.py` | 本地适配器:读 `backlog.jsonl` |
| `backlog/feishu_docs.json` | **需求清单**(飞书文档 token/标题/优先级/archetype) |
| `backlog/feishu_state.json` | **去重账本**:记已处理需求,`status=done` 的不重复跑 |
| `specs/FS-001.md` `specs/FS-002.md` | 需求原文快照(从飞书拉下来落地的 Spec 文本) |
| `trigger/webhook.py` | 事件式触发:监听 :8787,POST /trigger 跑一批(进程内 Lock,busy 返 409) |
| `trigger/index.html` | webhook 的"跑一批"按钮页 |
| `trigger/poll.sh` | 轮询式触发:每隔 N 秒自动跑一批(可选) |

### 4.2 生成引擎 `loop/engine/`(真正生成代码的黑盒)

| 文件 | 作用 |
|---|---|
| `generate.sh` | **引擎入口**。串起:生成 → 验收 → 确定性校验。按 `HARNESS_VERIFY_SOURCE=auto` 有无 acceptance.json 分流验收器 |
| `config.env` | 引擎配置(含 `HARNESS_VERIFY_SOURCE=auto` 形态分流开关) |
| `constraints.json` | 全局硬约束(所有生成都不得违反) |
| `prompt.md` | catalog 形态的系统提示词模板 |
| `prompt.spec.md` | **Spec 形态的系统提示词模板**(围绕交互/验收标准生成) |
| `tools/run_model.py` | **调 LLM 生成代码**。`build_context()`=catalog,`build_context_spec()`=Spec |
| `tools/verify.py` | catalog 验收器(20 项检查) |
| `tools/verify_ac.py` | **Spec 验收器**:逐条跑 acceptance.json 的 TC/AC |
| `tools/spec_compiler.py` | **Spec 编译器**:需求原文 → case。`--archetype spec` 产 Spec 三件套,否则产 catalog |
| `tools/compile_spec.py` | catalog 契约推导 / contract_gate |
| `tools/build_schema.py` | 数据 schema 构建 |
| `tools/sample_generator.py` | 离线参考生成器(零密钥,sample 模式用) |
| `rules/base/*.md` | 4 条通用规则(documentation/error-and-logging/security/testing) |
| `rules/task/*.md` | 3 条任务规则(conventions/structure/tech-stack) |
| `schemas/*.data.schema.json` | 三个 catalog 用例的数据 schema |
| `studio/server.py` | **配置平台后端**(Flask):约束/用例编辑 API + `/api/trigger` 触发 |
| `studio/templates/index.html` `login.html` | 配置平台前端页面 + 登录页 |
| `studio/static/css/studio.css` `js/studio.js` | 配置平台前端资源 |
| `studio/spec_render.py` | Spec 渲染辅助 |
| `cases/<name>/` | 各需求编译后的 case(catalog:case.json+三件套;Spec:spec/manifest+acceptance+spec.md) |

### 4.3 平台前端 `loop-platform/`

| 文件 | 作用 |
|---|---|
| `index.html` | 单文件 SPA(Dashboard/需求/Trace/一键交付),由 loop-spa :5200 托管 |

### 4.4 部署与运维 `loop/pipeline/deploy/`

| 文件 | 作用 |
|---|---|
| `setup_ecs.sh` | **ECS 一键部署**:装依赖→拉/更新代码→建 venv→校验 .env→自检→装三个 systemd 服务。幂等 |
| `sync_to_ecs.py` | **本地直传部署**:打包 loop/pipeline/loop/engine/loop-platform → scp 到 ECS → 解包 → 跑 setup |
| `ecs_exec.py` | ECS 远程命令执行辅助 |
| `loop-platform.service` | webhook(:8787)systemd 单元模板 |
| `loop-studio.service` | 配置平台(:5100)systemd 单元模板 |
| `loop-spa.service` | SPA 前端(:5200)systemd 单元模板 |
| `.env`(不进仓) | **所有密钥**:DEEPSEEK / FEISHU / GITHUB_TOKEN / ECS_SSH_PASSWORD / STUDIO_TOKEN |

## 六、完成过程(这个项目是怎么一步步搭起来的)

1. **先做引擎(harness 系列)**:harness → harness-2/3/4 逐代演进,把"LLM 生成代码 + 自动验收 + 确定性校验"打磨成一个可靠黑盒。harness-4 支持 catalog 与 Spec 两种形态。
2. **再做编排(loop/pipeline)**:在引擎外套一层大脑,接飞书需求源、串起编译→生成→发布→部署,把"人工跑一次"升级成"取需求自动跑一批"。
3. **加触发器**:webhook(:8787 事件式)+ poll(轮询式),让批处理变成可被按钮/事件驱动的 Loop。
4. **做配置平台(studio :5100)**:可视化编辑约束/用例、一致性预检、页面上直接点"🚀开始交付"。
5. **做 SPA 前端(:5200)**:Dashboard/需求/Trace 的精美壳。
6. **上生产**:`sync_to_ecs.py` 直传 + `setup_ecs.sh --with-service` 装三服务常驻,GitHub Actions 自动把 sampleN 部署到 1000+N 端口。
7. **本次收尾(方案 A)**:把番茄钟需求 FS-002 从 catalog 形态改造为 Spec 形态(真出计时器而非列表站),端到端在 ECS 跑通,并把 studio 从回环改成公网可访问。

## 七、踩过的坑(血泪清单)

| # | 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|---|
| 1 | **FLASK_RUN_FROM_CLI 泄漏** | 验收时服务不启动却 `code=0`,门禁误判通过 | studio 用 `flask run` 启动,注入 `FLASK_RUN_FROM_CLI=true` 被子进程一路继承,导致产物 app.py 的 `app.run()` 被 Flask 主动忽略 | 验收器起 app 前 pop 掉 FLASK_RUN_* 等环境变量(verify.py + verify_ac.py 都要打补丁) |
| 2 | **番茄钟变列表站** | Spec 需求被生成成 8 张卡片的目录站 | FS-002 在账本无 case 映射,每次都走 `compile_from_spec()`,而 spec_compiler 默认 catalog 形态重编译。改静态文件没用,每跑必被覆盖 | 账本标 `archetype=spec` + orchestrator 传 `--archetype spec` + config.env 分流 verify_ac + spec_compiler 清 catalog 残留 |
| 3 | **sync 还原运行态文件** | 本地改的 feishu_docs.json 部署后不生效 | `sync_to_ecs.py` 会备份+还原 ECS 侧 feishu_docs/state(保护运行态),所以本地对这俩的改动不随 tar 生效 | 部署后单独在 ECS 上打补丁改这两个文件 |
| 4 | **服务绑死回环,公网点不开** | 公网访问 :5100 秒拒 `http_code=000` | ExecStart 写死 `--host 127.0.0.1`,只监听本机 | 改成 `--host 0.0.0.0` + daemon-reload + 重启;安全组本就放行 |
| 5 | **openclaw-gateway 吃内存** | ECS OOM,交付进程被杀 | 无关的 openclaw 服务占内存 | 跑交付前确保 `systemctl stop openclaw-gateway`(现已 inactive) |
| 6 | **flask reloader 跟错 PID** | systemd 管的 PID 和真进程对不上 | `python server.py` 的 debug reloader 会 fork 子进程 | 用 `flask run`(关 reloader),server.py 本身不改 |
| 7 | **write_case_spec 不清残留** | Spec 编译后 run_model 却退回 catalog | 旧 case.json 残留在目录里,run_model 优先认它 | spec_compiler 编译时主动删除 case.json 等 catalog 残留 |
| 8 | **macOS `._*` 垃圾文件** | spec 目录混入 `._acceptance.json` 等 | macOS tar/传输带出的 AppleDouble 文件 | 部署时清理 `._*` |
| 9 | **GitHub 推送 403** | 推 loop-sample 失败 | token 权限不足 | 必须 classic PAT 且勾 `repo` scope,变量名全大写 `GITHUB_TOKEN` |
| 10 | **SSH 每命令新连接触发限流** | sshd 拒连 | 为每条命令新开 ssh 连接 | 用 pty 单连接复用 / ControlMaster,一次会话跑多条 |
| 11 | **shasum not found** | 确定性校验日志报 `shasum: command not found` | ECS 上无 shasum 命令 | 影响轻微(仍走 sha256sum 兜底);已知,不阻断 |

## 八、关键操作速查

```bash
# 【状态】看三个平台服务
systemctl status loop-studio loop-platform loop-spa
journalctl -u loop-studio -f          # 实时日志

# 【重启】(改代码/配置后)
systemctl restart loop-studio loop-platform loop-spa

# 【触发一批交付】(在 ECS 本机)
curl -X POST http://127.0.0.1:5100/api/trigger \
  -H "X-Studio-Token: <STUDIO_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"task":"FS-002","mode":"real"}'

# 【重跑某需求】删 state 里的条目使其可再跑
# 编辑 loop/pipeline/backlog/feishu_state.json 删掉对应 key

# 【更新代码 + 重装服务】(幂等)
cd /root/loop-platform && bash loop/pipeline/deploy/setup_ecs.sh --with-service

# 【本地直传部署】(在开发机仓库根)
.venv/bin/python loop/pipeline/deploy/sync_to_ecs.py sync
```

## 九、安全须知

- `.env`(600 权限)存所有密钥,**永不进 git**(.gitignore + 推送前复检)。
- studio :5100 现已公网可达,**唯一的锁是 `STUDIO_TOKEN`**——而它背后是会烧钱(LLM)、会推仓、会部署的"开始交付"按钮。建议二选一收紧:安全组只放行你的出口 IP,或换更长的强口令。
- sampleN 成品(:1000+N)是静态展示应用,公网全放行无妨。
- webhook :8787 与 SPA :5200 仍绑回环,走 SSH 隧道访问,零公网暴露。
