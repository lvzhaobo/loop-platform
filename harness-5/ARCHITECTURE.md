# harness-5 · Loop Engineering 理论骨架(Workshop 讲义)

> 这一页是"为什么这么搭"的理论底座。配合五层阶梯(L0→L4)食用:阶梯讲"怎么一步步搭",
> 本页讲"骨架长什么样、每个部件为什么存在"。可直接投屏。

---

## 一、一句话

> **Loop Engineering = 搭一套 Harness(可控环境),在里面把 Maker / Checker / Loop Engine 三个部件接成闭环,再逐层加约束,把非确定性的模型输出"框"进可预测的轨道。**

---

## 二、核心组件图

```
                    ┌─────────────────────────────────────────────┐
                    │                 HARNESS(可控环境)             │
                    │   前馈约束:rules / AGENTS.md / spec / facts   │
                    │             constraints(宪法)                │
                    │                                               │
   任务/需求 ─────▶ │   ┌─────────┐   产物    ┌──────────┐          │
                    │   │  Maker  │ ────────▶ │ Checker  │          │
                    │   │ 生成器  │           │ 验收器   │          │
                    │   └─────────┘           └──────────┘          │
                    │        ▲                     │                │
                    │        │   ④ 回喂失败报告      │ PASS/FAIL      │
                    │        └─────────────────────┘  (逐条 AC/TC)  │
                    │                     │                          │
                    │             ┌───────▼────────┐                 │
                    │             │  Loop Engine   │  ← 护栏:迭代/花费/卡死 │
                    │             │ 编排+护栏+收敛  │  ← 收敛:全绿才停       │
                    │             └───────┬────────┘  ← 可观测:state落盘   │
                    └─────────────────────┼──────────────────────────┘
                                          ▼
                                  通过的产物(+ 可复现:同输入同哈希)
```

四个部件,一句话各自的职责:

| 部件 | 职责 | 一句话 | harness-5 落点 |
|------|------|--------|----------------|
| **Harness** | 可控环境 | 约束 + 契约 + 门禁,把输出"框"住 | `constraints.json` + `spec/` + `gates` |
| **Maker** | 生成 | 给上下文 → 拿产物 → 落盘(不做判断) | [`lib/model.py`](lib/model.py) |
| **Checker** | 验收 | 产物 → 逐条 PASS/FAIL + 报告 | [`lib/gates.py`](lib/gates.py) |
| **Loop Engine** | 编排 | 生成→验收→决策(通过/重试/放弃),带护栏与收敛判据 | `l2_loop` / `l3_guardrails` |

> ⚠️ **Harness 不是第四个文件**:它 = Checker + 它所依赖的 constraints/spec/facts。Checker 是"执行检查的手",判据来自约束与契约。

## 三、两条正交的轴:计算型/推理型 × 前馈/反馈

这是理解"约束到底加在哪、靠什么生效"的关键 2×2。

|              | **前馈(生成前注入)** | **反馈(生成后检查回喂)** |
|--------------|------------------------|----------------------------|
| **计算型/确定性** | rules、`AGENTS.md`、spec、facts、JSON Schema、模板 —— 注入是机械确定的 | lint、单测、类型、Schema 校验、字段规则、路由连通、行数、哈希 —— **客观、可复现、便宜** |
| **推理型/裁判型** | (少见)让模型"读需求自己推断风格" —— 不可控 | LLM-as-Judge、代码评审、意图/可读性/UI 还原度 —— **主观、要模型、贵、有噪声** |

三条要点:

1. **前馈约束的"注入"是确定的,但"生效"是概率的** —— rules/AGENTS.md 拼进上下文这一步是机械的;但模型读了未必照做。所以必须有反馈的计算型门禁去兜底。
2. **前馈抬高概率,反馈焊死下限** —— 只有前馈 = 祈祷模型听话;加上反馈计算型门禁,才把质量下限钉死。
3. **能用计算型就别用推理型** —— 计算型便宜可复现;推理型只补计算型覆盖不到的"意图/质量"维度,且必须配 rubric + 温度0 + 阈值。

## 四、验收门禁分级:AC → TC → 门禁结果

验收不是"打个分",而是**逐条可追溯的二值门禁**:

```
AC(验收标准,来自 spec)
  └── TC(测试用例,可执行)
        └── 门禁结果(PASS / FAIL) —— 阻断级不过就 fail,循环继续
```

- **AC(Acceptance Criteria)**:规格里"算通过"的条件。harness-5 里 = `spec.md` 的函数契约 / `spec-mall.md` 的数据与 UI 规范。
- **TC(Test Case)**:把 AC 变成能跑的判定。harness-5 里 = `tests/test_mathkit.py` 每条断言 / mall 的数据+标记校验。
- **门禁分级**:阻断级(TC 不过 → fail,Loop 继续)vs 建议级(记录但不阻断)。评分只作为推理型软性补充,不当硬门禁。

> harness-5 现状:`gates.verify` 逐项 `record` 出 PASS/FAIL 已是这个雏形;尚未显式做"阻断级 vs 建议级"分级——这是可扩展点。

## 五、映射到五层阶梯

| 层 | 加了什么 | 对应骨架部件 |
|----|----------|--------------|
| **L0** | 只有 Maker,裸调 | Maker |
| **L1** | + Harness(约束+自洽性+验收门禁) | Maker + Checker + 前馈约束 |
| **L2** | + Loop(失败回喂,重试到通过) | + Loop Engine(回喂 + 收敛判据) |
| **L3** | + 护栏(迭代/花费/卡死上限) | Loop Engine 的护栏 |
| **L4** | + 确定性(temp0+seed,重跑比对哈希) | 可复现(主流产品普遍不做的差异点) |

---

## 六、一句话收束

> **稳定生成 = 前馈把出错概率往上抬 + 反馈的计算型门禁把质量下限焊死 + Loop 把两者接成会自愈的闭环 + 护栏防止失控 + 确定性保证可复现。**

计算型/推理型这条轴**同时贯穿前馈和反馈**;AC/TC 是验收门禁的可追溯骨架;Maker/Checker/Loop 是三个可复用部件,换任务(mathkit↔mall)只换 spec/facts/constraints 三份声明,部件不动——这就是"框架任务无关"。
